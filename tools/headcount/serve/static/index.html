1. Which metric grew?

Question: which metric names gained the most series in the window, compared with the window of the same length just before it?

In Mimir picks the cheapest read for the window. A window that is exactly one day (one block range) is read from the index-headers: for every name the index records where its list of series starts and ends, and each entry is 4 bytes, so the length is the count. Any other window reads series entries and chunk metas from the full index, and a window across days removes duplicates. The cost column says which read was used.

Baseline is count by (__name__) over the window, which loads every series and its chunks.

Truth is the generator's own count, before → window. Click a row to use that metric in panels 2 to 4.

What panel 1 cost: the same ranking answered both ways. Both count every metric name in the window and in the window before it. Compare latency and what was read. Headcount never reads chunks.

2. Which label exploded?

Question: the metric grew, but which label is to blame? Every label of the metric is counted by distinct values, in the window and in the window before it, and ranked by growth. The top label is then shown as bars, with its largest values.

In Mimir looks up the metric's series in the index and counts them per label value. It reads series labels but no chunks.

Baseline is count by (<label>), which loads the chunks too.

3. When did it start?

Question: within the window, when did the selected metric start growing? The window is cut into buckets of the Step: auto picks hours for a window of a day or less and days otherwise. This is the API's step, and matches a PromQL range query whose step equals its range selector.

In Mimir uses chunk metas: the index records each chunk's first and last timestamp, so a series counts in a bucket if one of its chunks overlaps it. The chunks themselves are not read.

Baseline is a PromQL range query with the same step. Bars are Headcount, dots are the baseline; they should sit on each other.

4. It can't become an incident

Question: what happens when a request is too big to answer cheaply?

In Mimir each store-gateway stops after the budget (the "Budget and series limit" box) and returns what it counted so far, marked as a lower bound. You get a partial answer, not an outage. The budget applies per store-gateway, so with several store-gateways the lower bound can be up to the budget times their number.

Baseline with the same series limit fails with an error. Change the budget and press Run to see both move.

5. Distinct series over the whole window

Question: how many distinct series existed over the whole window?

Each day is a separate block range (here split by the compactor into several shard blocks). A series that lives on two days is in both ranges, so adding each day's count counts it twice. That is the dashed card, too high on purpose to show the problem.

In Mimir removes the duplicates: each store-gateway returns a hash of every series' labels and the querier counts distinct hashes. It should equal the truth and the baseline.

If the window is inside one day, there is nothing to deduplicate and both agree. Pick a window across days to see the difference.

The window is inside one day, so there is nothing to deduplicate: Headcount, adding the days and the truth all read series. The difference only shows across days.
